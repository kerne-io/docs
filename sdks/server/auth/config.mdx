---
title: "Auth config"
description: "Read the tenant's current auth configuration"
---

Public route (no auth required) - useful for rendering the right signup form before you know who's asking.

```typescript
const config = await kerne.auth.config();
```

```json
{
  "registration_mode": "OPEN",
  "enable_magic_link": false,
  "enable_credentials": true,
  "oauth_providers": [],
  "show_kerne_branding": true,
  "brand_primary_color": null,
  "brand_logo_url": null,
  "portal_redirect_url": null,
  "portal_url": null,
  "post_auth_redirect_url": null,
  "user_registration_limit": null,
  "app_name": "Acme",
  "password_policy": {
    "min_length": 8,
    "require_uppercase": false,
    "require_number": false,
    "require_symbol": false
  }
}
```

`password_policy` is what the server will actually accept - render your signup form's rules from it instead of hardcoding them, so a stricter policy set later doesn't silently start rejecting submissions your form told the user were fine. It's optional on the type only because this response is cached for an hour: a client that fetched it just before the field shipped won't see it until the cache turns over.

See [Registration modes](/concepts/identity/registration-modes) for what `registration_mode` controls.

`portal_url` is where to actually send an unauthenticated visitor to reach the hosted portal (`apps/portal`) - every auth and billing flow (sign-up, magic link, password reset, email verification, checkout) resolves there, null only if no portal is deployed for this environment. `post_auth_redirect_url` is the opposite direction: where the portal sends the session back once it's done, `= portal_redirect_url ?? app_url`.

<Note>
  The live endpoint also returns a handful of dashboard-only settings (onboarding state, token TTLs, the tenant's chosen overview tiles) that this SDK's `AuthConfig` type deliberately leaves untyped - they describe Kerne's own console, not something a client-side integration acts on.
</Note>
