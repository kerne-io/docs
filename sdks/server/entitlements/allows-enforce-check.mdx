All three resolve the exact same entitlement - they only differ in what they hand back. Pick based on what you're about to do with the answer.

```typescript
// UI conditional, or any branch where a plain boolean is enough
const canExport = await kerne.allows('export_pdf', { subject: userId });

// Guard/middleware - let it throw instead of checking a boolean yourself
await kerne.enforce('export_pdf', { subject: userId });

// You need the detail (a quota's limit/used/remaining), not just yes/no
const result = await kerne.check('api_calls', { subject: userId });
// { allowed, feature_key, feature_type, limit, used, remaining, overage_behavior, has_override, ... }
```

## Parameters

<ParamField path="featureKey" type="string" required>
  The feature's key, as configured in the dashboard.
</ParamField>
<ParamField path="subject" type="string">
  Whose entitlement to check - a Kerne user id, the same one the subscription was created against. Optional in the type, but with a secret key there's no "current user", so pass it explicitly.
</ParamField>
<ParamField path="requested" type="number">
  For quota features: "can this subject use `requested` more units?" - defaults to `1`.
</ParamField>
<ParamField path="dimension" type="string">
  For a feature whose limit binds per dimension (per machine, per project, per seat): which slice to check. The SDK param is `dimension`; it goes on the wire as `dimension_id`. See [`consume()` > Dimensions](/sdks/server/entitlements/consume#dimensions) for the full behavior.
</ParamField>

## `enforce()` throws `EntitlementDeniedError`

`enforce()` runs the same `check()` and throws when `allowed` is `false`. The throw is an `EntitlementDeniedError` - a `KerneError` subclass, so `instanceof KerneError` / `isKerneError()` catch it - with:

- `.check` - the full `EntitlementCheck` (`allowed`, `limit`, `used`, `remaining`, `access_limit`, `overage_behavior`, `configured`, `has_override`, ...), so a guard can branch on *why* access was denied without a second call.
- `.code === 'ENTITLEMENT_DENIED'`, `.statusCode === 403`, `.type === 'AUTHORIZATION_ERROR'`.
- `.requestId` unset - it's built client-side from a successful (200) `check()`, not from an API error response.

The message text is unchanged (`Entitlement denied for feature '<key>'`), so a bare `catch (e) { e.message }` still works; use `instanceof` only when you branch on the shape.

```typescript
import { EntitlementDeniedError } from '@kerne/server';

try {
  await kerne.enforce('api_calls', { subject: userId });
} catch (err) {
  if (err instanceof EntitlementDeniedError) {
    // err.check.configured === false  -> misconfigured, not "upgrade"
    // err.check.remaining, err.check.overage_behavior -> quota vs hard stop
    return res.status(403).json({ error: 'upgrade_required' });
  }
  throw err;
}
```

## Reading the result of `check()`

`check()` returns an `EntitlementCheck`. Every field, and whether to gate on it:

| Field | Meaning | Use for access control? |
| --- | --- | --- |
| `allowed` | May the subject do this **right now** | **Yes - this is the gate** |
| `configured` | Did the catalog or an override say anything about this feature for this subject | No - diagnostics only |
| `feature_type` | `BOOLEAN` / `QUOTA` / `STATIC`, or `UNKNOWN` for a key that doesn't exist | Branch on it for display |
| `enabled` | Boolean features: the resolved on/off value | Same as `allowed` for a boolean; still gate on `allowed` |
| `limit` / `used` / `remaining` | Quota features: the included allowance, consumed so far, and what's left (`null` = unlimited) | Display and your own logic; still gate on `allowed` |
| `access_limit` | Where access actually stops: equal to `limit` under `BLOCK`, otherwise the overage ceiling, or `null` when there is none | Advanced |
| `overage_behavior` | `BLOCK` / `ALLOW` / `BILL` - what happens past `limit` | Display / UX |
| `cap_reached` | Spending cap hit; billing has stopped, consumption has not | **No - not an access signal by itself** |
| `has_override` | An admin override applies to this subject and feature | Informational |
| `subscription_status` | The subject's subscription status, or `NONE` | Display |
| `value` | Static features: the config value, returned as-is | Read it; `allowed` mirrors `configured` for static |

<Warning>
`remaining` is plain subtraction and **does** go negative once a subject runs past what its plan includes. On a feature whose overage is `ALLOW` or `BILL`, `allowed` stays `true` there - the subject hasn't hit a wall, they've started paying. Read `overage_behavior` before turning a negative `remaining` into "limit reached". `used` itself is never negative: a credit (rollover, or an [admin adjustment](/sdks/server/admin/usage-corrections)) is folded into `limit` instead.
</Warning>

### `configured` vs `allowed`

`allowed` is the go/no-go. `configured` only tells you whether the catalog (or an override) *said anything* about this feature for this subject.

On the public check path the two always deny together - `configured: false` implies `allowed: false` - in every one of these cases:

- the feature key does not exist (`feature_type: 'UNKNOWN'`)
- the subject has no subscription **and** no override **and** no active default plan
- an offer version resolved, but this feature isn't in it and there is no override

Do **not** treat `configured: false` as "open by default". Read it only when you must tell "not sold yet" apart from "sold and denied" - a diagnostic, or a documented fallback while the catalog is still being filled in.

| Situation | `configured` | `allowed` |
| --- | --- | --- |
| Included, and within the allowance | `true` | `true` |
| Excluded (off, or allowance exhausted under `BLOCK`) | `true` | `false` |
| Feature missing from the offer / no offer / unknown key | `false` | `false` |
| Active override applies | `true` | by override value |

See [Entitlements](/concepts/monetization/entitlements) for the three kinds of capability.
