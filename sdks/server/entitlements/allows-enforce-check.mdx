sidebarTitle: "Check an entitlement"

---

All three resolve the exact same entitlement - they only differ in what they hand back. Pick based on what you're about to do with the answer.

```typescript
// UI conditional, or any branch where a plain boolean is enough
const canExport = await kerne.allows('export_pdf', { subject: userId });

// Guard/middleware - let it throw instead of checking a boolean yourself
await kerne.enforce('export_pdf', { subject: userId });

// You need the detail (a quota's limit/used/remaining), not just yes/no
const result = await kerne.check('api_calls', { subject: userId });
// { allowed, feature_key, feature_type, limit, used, remaining, overage_behavior, has_override, ... }
```

## Parameters

<ParamField path="featureKey" type="string" required>
  The feature's key, as configured in the dashboard.
</ParamField>
<ParamField path="subject" type="string">
  Whose entitlement to check - a Kerne user id, the same one the subscription was created against. Optional in the type, but with a secret key there's no "current user", so pass it explicitly.
</ParamField>
<ParamField path="requested" type="number">
  For quota features: "can this subject use `requested` more units?" - defaults to `1`.
</ParamField>
<ParamField path="dimension" type="string">
  For a feature whose limit binds per dimension (per machine, per project, per seat): which slice to check. The SDK param is `dimension`; it goes on the wire as `dimension_id`. See [`consume()` > Dimensions](/sdks/server/entitlements/consume#dimensions) for the full behavior.
</ParamField>

## `enforce()` throws `EntitlementDeniedError`

`enforce()` runs the same `check()` and throws when `allowed` is `false`. The throw is an `EntitlementDeniedError` - a `KerneError` subclass, so `instanceof KerneError` / `isKerneError()` catch it - with:

- `.check` - the full `EntitlementCheck` (`allowed`, `limit`, `used`, `remaining`, `access_limit`, `overage_behavior`, `configured`, `has_override`, ...), so a guard can branch on *why* access was denied without a second call.
- `.code === 'ENTITLEMENT_DENIED'`, `.statusCode === 403`, `.type === 'AUTHORIZATION_ERROR'`.
- `.requestId` unset - it's built client-side from a successful (200) `check()`, not from an API error response.

The message text is unchanged (`Entitlement denied for feature '<key>'`), so a bare `catch (e) { e.message }` still works; use `instanceof` only when you branch on the shape.

```typescript
import { EntitlementDeniedError } from '@kerne/server';

try {
  await kerne.enforce('api_calls', { subject: userId });
} catch (err) {
  if (err instanceof EntitlementDeniedError) {
    // err.check.configured === false  -> misconfigured, not "upgrade"
    // err.check.remaining, err.check.overage_behavior -> quota vs hard stop
    return res.status(403).json({ error: 'upgrade_required' });
  }
  throw err;
}
```

## Reading the result of `check()`

`used` is never negative, even when the subject is carrying a credit (a rollover or an [admin adjustment](/sdks/server/admin/usage-corrections)) - a credit is folded into `limit` instead.

`remaining` is plain subtraction and **does** go negative once a subject runs past what its plan includes. That's not an error state: on a feature whose overage is tolerated or billed, `allowed` stays `true` there. Check `overage_behavior` before turning a negative `remaining` into "limit reached" — see [Usage billing](/concepts/monetization/usage-billing#why-the-cap-doesnt-block).

On `ALLOW`/`BILL`, `allowed` still flips back to `false` once usage passes `access_limit` - a separate, optional hard ceiling in units (not the same thing as a spending cap), `null` when the feature has none.

See [Entitlements](/concepts/monetization/entitlements) for the full type breakdown (boolean/quota/static) and what each field means per type.
