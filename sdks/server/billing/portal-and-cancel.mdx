## Billing portal

A hosted page (Stripe/Polar) where the caller manages their own payment method, invoices, and plan - for the caller's own identity, same as [checkout](/sdks/server/billing/checkout).

```typescript
const { url } = await kerne.billing.portal({ returnUrl: 'https://app.example.com/settings' });
```

If you don't pass `returnUrl`, it's resolved the same cascading way as checkout's `successUrl`/`cancelUrl` - see [Checkout](/sdks/server/billing/checkout#where-the-redirect-goes-if-you-dont-pass-successurlcancelurl).

## Cancel

```typescript
// Cancel the caller's own active subscription
await kerne.billing.cancel({ immediately: false }); // false = at period end (default)

// Cancel a specific subscription (admin, any subject)
await kerne.billing.subscriptions.cancel(subscriptionId, /* immediately */ true);
```

`immediately: false` keeps access through the current period's end - the common choice, since an abrupt cutoff mid-period is rarely what you want for a self-service cancel. It only stamps `canceled_at`: `status` doesn't move to `CANCELED` until the provider's own period-end webhook confirms it later. `immediately: true` flips `status` to `CANCELED` right away instead. Check `canceled_at`, not `status`, if your UI needs to show "cancellation scheduled" before that webhook arrives.

Either way the row is never deleted: the billing history stays readable, and the subject can subscribe again without losing what came before.

`kerne.billing.cancel()` throws a plain `Error` (not a `KerneError`) if the caller has no subscription at all - it's a client-side guard, not a server response, same reasoning as [`enforce()`](/sdks/server/entitlements/allows-enforce-check#enforce-throws-a-plain-error). `kerne.billing.subscriptions.cancel(id, ...)` has no such check; a bad `id` fails with the server's own 404 instead.

<Note>
  The provider is told first, then Kerne. A cancellation really stops the next invoice rather than only closing off access on our side - which is the failure mode this ordering exists to prevent.
</Note>

## Change plan

```typescript
await kerne.billing.subscriptions.changePlanPrice(subscriptionId, nextPlanPriceId);

// Skip the provider settling the difference, and just charge the new price next invoice
await kerne.billing.subscriptions.changePlanPrice(subscriptionId, nextPlanPriceId, {
  prorationBehavior: 'none',
});
```

The swap is **immediate**, upgrade or downgrade alike, and the provider prorates by default.

The subscription's entitlements move with it: `changePlanPrice()` re-pins the pack, so what the subject is allowed to do reflects the new plan on the next check. Deferring a downgrade to the end of the period is not supported yet - see [Products & plans](/concepts/monetization/products-and-plans) for how a pack is pinned in the first place.

<Warning>
  The second argument is a **`plan_price_id`** - a specific billing variant (monthly vs. yearly), not a plan id.
</Warning>
