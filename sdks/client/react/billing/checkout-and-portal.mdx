```tsx
import { useCheckout } from '@kerne/react';

function UpgradeButton({ planPriceId }: { planPriceId: string }) {
  const { openCheckout } = useCheckout();

  return (
    <button onClick={() => openCheckout(planPriceId, { successUrl: '/billing/success' })}>
      Upgrade
    </button>
  );
}
```

<Warning>
The first argument is a **`plan_price_id`** (a specific billing variant - monthly vs. yearly), not a plan id.
</Warning>

`openCheckout()` redirects the browser directly (`window.location.href = url`). If you want the URL instead - to open in a new tab, or handle the redirect yourself - use `createCheckout()`, which returns the URL without navigating:

```tsx
const { createCheckout } = useCheckout();

const checkoutUrl = await createCheckout(planPriceId);
```

The billing portal works the same way, via `usePortal()`:

```tsx
import { usePortal } from '@kerne/react';

const { openPortal, createPortal } = usePortal();

await openPortal(); // redirects the browser
const portalUrl = await createPortal(); // or get the URL yourself
```

## Where the redirect goes if you don't pass a URL

`successUrl`/`cancelUrl`/`returnUrl` above are all optional. Left unset, each resolves independently through your tenant's configured `app_url` before falling back to a Kerne-hosted page - see the server SDK's [Checkout docs](/sdks/server/billing/checkout#where-the-redirect-goes-if-you-dont-pass-successurlcancelurl) for the exact resolution order and how to configure `app_url`.

## The caller's own subscription

The reactive hook covers most cases:

```tsx
import { useSubscription } from '@kerne/react';

const { subscription, isActive, isLoading, refetch } = useSubscription();
```

For an imperative, one-off read, use the underlying client directly:

```tsx
import { useClient } from '@kerne/react';

const client = useClient();
const sub = await client.getSubscription(); // null if none, or scoped to a product slug: getSubscription('acme')
```

## Cancelling and switching plans

Both act on the payment provider first, then on Kerne — so a cancellation really stops the next invoice, rather than only closing off access on our side.

```tsx
import { useCancelSubscription, useChangePlan, useSubscription } from '@kerne/react';

function ManagePlan() {
  const { subscription, refetch } = useSubscription();
  const { cancelSubscription, isCanceling } = useCancelSubscription();
  const { changePlan, isChanging } = useChangePlan();

  if (!subscription) return null;

  return (
    <>
      <button
        disabled={isChanging}
        onClick={async () => {
          await changePlan(subscription.id, nextPlanPriceId);
          refetch();
        }}
      >
        Switch plan
      </button>

      <button
        disabled={isCanceling}
        onClick={async () => {
          await cancelSubscription(subscription.id);
          refetch();
        }}
      >
        Cancel
      </button>
    </>
  );
}
```

Neither hook refreshes `useSubscription()` for you — there is no shared cache to invalidate — so call `refetch()` once the action resolves if the same screen displays the subscription.

<Note>
  A plan change takes effect **immediately**, upgrade or downgrade alike, and the provider settles the difference by default. Pass `{ prorationBehavior: 'none' }` to skip that and simply charge the new price from the next invoice. Deferring a downgrade to the end of the period is not supported yet.
</Note>

`cancelSubscription(id)` ends the subscription at the end of the paid period. Pass `true` as the second argument to end it immediately instead. Either way the row survives with status `canceled` — cancelling is not deleting, and the billing history stays readable.

## Building a plan picker

A page that lets a visitor pick any plan doesn't know upfront whether they're a new signup or already subscribed — and that distinction matters more than it looks. Starting a fresh checkout for someone already subscribed doesn't replace their subscription: Stripe and Polar have no notion of "this session replaces the one on file", so it creates a second, independent subscription while the first keeps billing. `usePlanSwitch()` makes that decision once, for every screen that needs it — it's what [`<PricingTable>`](/sdks/client/react/ui/pricing-table) and the plan switcher inside `<UserProfile>` use internally:

```tsx
import { usePlanSwitch, useSubscription } from '@kerne/react';

function PlanPicker({ plans }) {
  const { subscription, refetch } = useSubscription();
  const { pending, switching, selectPlan, confirmSwitch, dismissSwitch } = usePlanSwitch(
    subscription,
    refetch,
  );

  return (
    <>
      {plans.map((plan) => (
        <button key={plan.id} onClick={() => selectPlan(plan, plan.prices[0])}>
          {plan.name}
        </button>
      ))}

      {pending ? (
        <ConfirmDialog loading={switching} onConfirm={confirmSwitch} onCancel={dismissSwitch}>
          Switch to {pending.plan.name}?
        </ConfirmDialog>
      ) : null}
    </>
  );
}
```

No subscription yet (`subscription` is `null`) sends `selectPlan` straight to `openCheckout()` instead — there's nothing to swap, so `pending` never gets set for that visitor. `switchError`, `checkoutError` and `checkoutPriceId` (busy state through the checkout redirect) are also on the return value, same idea as `isCanceling`/`isChanging` above.
