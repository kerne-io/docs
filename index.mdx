Pricing changes. Plans get restructured. Some customers keep the deal they signed up on, someone negotiates an exception, and usage grows past whatever looked generous when you first wrote the number down.

All of that eventually ends up in your application code:

```typescript
if (user.plan === 'pro') { /* ... */ }
if (subscription.status === 'active') { /* ... */ }
if (usage < 10_000) { /* ... */ }
```

Every one of those lines is a commercial decision written in a place you have to redeploy to change. And there is never just one of them.

## What Kerne does

Kerne keeps those rules outside your application.

Your payment provider tells Kerne what a customer bought. You define what that buys them. Kerne tracks the rest — which version of your offer they're on, what they've consumed this period, what was negotiated with them, whether their last payment went through — and turns all of it into an answer your application can act on:

> **Can this person do this, right now?**

```typescript
if (await kerne.allows('export_pdf', { subject: userId })) {
  return generatePdf();
}
```

Your application doesn't need to know which plan they're on, how that plan is priced, what they've used this month, or what exception applies to them.

It needs to know what they're allowed to do.

**Kerne is the authorization layer for monetized software.**

## What that changes

<AccordionGroup>
  <Accordion title="You can change your pricing without changing what existing customers get" icon="clock-rotate-left">
    Raise a limit, move a feature to a pricier tier, restructure the whole lineup — the people already
    subscribed keep exactly what they signed up for, until you decide to move them. That is the
    default, not something you remember to switch on.

    See [what a plan grants, and how it changes](/concepts/monetization/products-and-plans#changing-your-offer-without-changing-your-customers).
  </Accordion>
  <Accordion title="An exception is a setting, not a branch in your code" icon="user-pen">
    A customer negotiates 1,000 a month instead of 200. You don't invent a plan for them and you don't
    write `if (customer.id === ...)`. You grant the exception, and every check that already exists
    starts returning the right answer for that one customer.

    See [overrides](/sdks/server/admin/overrides).
  </Accordion>
  <Accordion title="A limit that blocks and a limit that bills are the same line of code" icon="gauge">
    "Stop at 5 seats" and "keep going past 10,000 emails and charge for the rest" are the same call in
    your app. Which one happens is decided on the plan, per feature — and can be different on every
    plan.

    See [usage billing](/concepts/monetization/usage-billing).
  </Accordion>
</AccordionGroup>

## Where the money moves

Kerne is not a payment processor. Stripe still moves the money, holds the card details, and handles the legal side of billing.

The split is clean: your provider is told what to charge, Kerne decides what that entitles someone to. Which means your own code never names a plan, a price, or a provider.

## In your app

<CodeGroup>

```typescript Server (@kerne/server)
import { Kerne } from '@kerne/server';

const kerne = new Kerne({
  appId: process.env.KERNE_APP_ID!,
  secretKey: process.env.KERNE_SECRET_KEY!, // sk_live_...
});

// Gate on the capability, never on the plan name
if (await kerne.allows('export_pdf', { subject: userId })) {
  return generatePdf();
}
```

```tsx React (@kerne/react)
import { KerneProvider, Access } from '@kerne/react';

function Root() {
  return (
    <KerneProvider appId={process.env.NEXT_PUBLIC_KERNE_APP_ID!}>
      <App />
    </KerneProvider>
  );
}

function ExportButton() {
  return (
    <Access featureKey="export_pdf" fallback={<UpgradePrompt />}>
      <button onClick={exportPdf}>Export as PDF</button>
    </Access>
  );
}
```

</CodeGroup>

## Before you build against it

Kerne makes some choices deliberately, and a few of them decide whether it fits your product at all — chiefly that access is granted to individual users today, not to a company or a team as one unit.

[**Is Kerne a fit?**](/guides/is-kerne-a-fit) covers that honestly, in five minutes, before you design around the model.
