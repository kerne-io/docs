# The authorization layer for monetized software

**Your pricing changes. Your customers change. Your product shouldn't have to.**

Kerne keeps the rules between what a customer bought and what your application lets them do out of your code.

## The problem

Every commercial decision eventually lands in a source file:

```typescript
if (user.plan === 'pro') { /* ... */ }
if (subscription.status === 'active') { /* ... */ }
if (usage < 10_000) { /* ... */ }
```

Each of those is a business rule written somewhere you have to redeploy to change. And there is never just one of them — they spread across services, drift apart, and quietly disagree.

## What Kerne does

Everything that should change what a customer can do goes in one side. One answer comes out the other.

```
      Pricing changes
     Customer upgrades
  Usage reaches a limit
Customer gets an exception
  Payment status changes
            │
            ▼
          Kerne
            │
            ▼
  What the customer can do
```

Your application asks one question, and never learns why the answer is what it is:

```typescript
if (await kerne.allows('export_pdf', { subject: userId })) {
  return generatePdf();
}
```

## How it works

<Steps>
  <Step title="Define what you sell">
    Create your offers and what each one includes, in the dashboard.
  </Step>
  <Step title="A customer gets a version">
    Their access is tied to the terms they actually received — not to whatever your catalog says
    today.
  </Step>
  <Step title="Your application asks Kerne">
    ```typescript
    await kerne.allows('export_pdf', { subject: userId });
    ```
  </Step>
  <Step title="Kerne makes the decision">
    Your application doesn't need to know whether that access came from a plan, an allowance already
    spent, a negotiated exception, a failed payment, or a version of your offer you stopped selling
    two years ago.

    That's the abstraction worth having.
  </Step>
</Steps>

## Where the money moves

Kerne is not a payment processor. Stripe still moves the money, holds the card details, and handles the legal side of billing.

The split is clean: your provider is told what to charge, Kerne decides what that entitles someone to. Your own code never names a plan, a price, or a provider.
