## What is Kerne?

Kerne is an entitlements engine, a usage meter, and a subscription lifecycle manager, sitting in front of Stripe.

It answers one question on every request:

> What is this user allowed to do, in this product, under this business context?

Stripe stays the actual payment processor — it moves money, holds card details, handles the legal side of billing. Kerne doesn't replace it: it decides who gets what, then tells Stripe what to charge, so your code never hardcodes a plan name.

Instead of scattering that logic across identity providers, billing systems, and `if (user.plan === 'pro')` checks, you call a single primitive:

```
User wants to do X  →  kerne.allows('X')  →  Kerne decides
→ allowed: your app does X
→ denied: your app shows an upgrade prompt
```

That one call — `allows()` — is what replaces scattered plan checks and duplicated business rules across your codebase.

## Is Kerne a fit for you?

Kerne is strongest when you gate **individual users** with entitlements, versioned plans, and optional usage billing. It is not yet a native fit for organization-level subjects, social OAuth, or fine-grained roles.

Read **[Is Kerne a fit?](/concepts/is-kerne-a-fit)** before you design against the model — five minutes that save weeks of wrong assumptions.

## What Kerne gives you

- **Entitlements per dimension** — meter a quota per machine, per project, or per seat inside one account, not just per account. See [Usage billing](/concepts/monetization/usage-billing).
- **A configurable billing lifecycle** — a grace period on failed payments before access is cut, and a cancel that either ends access right away or lets it run out the period already paid for.
- **No provider lock-in in your own code** — you call `kerne.billing.checkout()` / `subscription()`, never a payment provider's own API directly.
- **Hosted auth & billing portal** — when you don't want to build those screens yourself.
- **React hooks and prebuilt UI** — session, guards, pricing table, account management.

## What it doesn't do yet

- Bill or gate a **group of users as one unit** — a subject is always one individual user today.
- **Social / OAuth login** — only email + password and magic link.
- Fine-grained **roles or per-resource permissions** — admin access is a property of your secret key, not a per-user role.

Full detail: [Is Kerne a fit?](/concepts/is-kerne-a-fit) and [Platform foundations](/concepts/overview).

## SDK example

<CodeGroup>
```typescript Server (@kerne/server)
import { Kerne } from '@kerne/server';

const kerne = new Kerne({
appId: process.env.KERNE*APP_ID!,
secretKey: process.env.KERNE_SECRET_KEY!, // sk_live*...
});

// Gate an action behind an entitlement, not a plan name
if (await kerne.allows('export_pdf', { subject: userId })) {
return generatePdf();
}

````

```tsx React (@kerne/react)
import { KerneProvider, Access } from '@kerne/react';

function Root() {
  return (
    <KerneProvider appId={process.env.NEXT_PUBLIC_KERNE_APP_ID!}>
      <App />
    </KerneProvider>
  );
}

function ExportButton() {
  return (
    <Access featureKey="export_pdf" fallback={<UpgradePrompt featureKey="export_pdf" />}>
      <button onClick={exportPdf}>Export as PDF</button>
    </Access>
  );
}
````

## What's here today

- Identity — authentication, sessions, registration modes, waitlist, invitations
- Billing — plans, subscriptions, Stripe
- Entitlements — boolean, quota, and static capabilities granted by a plan
- Usage billing — rates, tiers, caps, dimensions

See Platform foundations for the exact current boundary.
