=== ./sdks/server/overview.mdx ===
---
title: "Overview"
description: "@kerne/server - your backend's Kerne client"
---

`@kerne/server` is the only place that should ever hold your secret key. It's what lets a request act on behalf of *any* scope, not just the caller - that's the whole reason it stays server-side.

## Install & configure

```bash
npm install @kerne/server
```

```typescript
import { Kerne } from '@kerne/server';

const kerne = new Kerne({
  appId: process.env.KERNE_APP_ID!,
  secretKey: process.env.KERNE_SECRET_KEY!, // sk_live_... or sk_test_...
  // baseUrl defaults to https://api.kerne.io
});
```

## The surface, by tier

The methods are grouped by *who* is meant to call them - not by resource - because that's what actually changes as you build:

<Steps>
  <Step title="Tier 1 - entitlements, flat on the client">
    The reason this SDK exists. No `.billing.` prefix - these are the calls you'll write the most.

    ```typescript
    kerne.allows(featureKey, { scope })       // boolean, never throws
    kerne.enforce(featureKey, { scope })      // throws if denied
    kerne.check(featureKey, { scope })        // full detail: limit/used/remaining/...
    kerne.consume(featureKey, { scope, delta })
    kerne.reportUsage(featureKey, { scope, delta })
    kerne.entitlements({ scope })
    kerne.usage({ scope, featureKey? })
    ```

    See [Entitlements & usage](/sdks/server/entitlements/allows-enforce-check).
  </Step>
  <Step title="Tier 2 - billing the end user touches">
    ```typescript
    kerne.billing.subscription()
    kerne.billing.plans(productIdOrSlug)   // public pricing data, read-only
    kerne.billing.checkout(planPriceId, options)
    kerne.billing.portal(options)
    kerne.billing.cancel(options)
    kerne.billing.subscriptions.list/get/cancel(...)
    ```

    See [Billing](/sdks/server/billing/subscription).
  </Step>
  <Step title="Tier 3 - identity & growth">
    ```typescript
    kerne.auth.*         // signup, login, password reset, email verification
    kerne.users.me/get/update(...)
    kerne.waitlist.*
    kerne.invitations.*
    ```

    See [Authentication](/sdks/server/auth/signup), [Users](/sdks/server/users/me), [Waitlist](/sdks/server/waitlist/join), [Invitations](/sdks/server/invitations/create).
  </Step>
  <Step title="Tier 4 - admin corrections, never from an end-user request">
    ```typescript
    kerne.admin.setUsage / adjustUsage / resetUsage(...)
    kerne.admin.grant / listGrants / revokeGrant(...)
    ```

    Same idea as `supabase.auth.admin.*` - one client, a namespace that signals "this call needs elevated trust." See [Admin](/sdks/server/admin/usage-corrections).
  </Step>
</Steps>

## Escape hatch

If a route you need isn't wrapped yet, `kerne.request()` calls it directly with the same authentication as everything else - see [Direct requests](/sdks/server/request).

## What this SDK does not do

Catalog management (products, plans, prices, packs) isn't in this SDK - that's control-plane configuration for your own dashboard, not something your app's backend does at runtime. Use the Kerne dashboard or `@kerne/contracts` for that.

```typescript
const { token, refresh_token, user, expires_at } = await kerne.auth.refreshToken({
```

<Warning>
`refresh_token` here means the value returned alongside `token` from signup/login - **not** the access token itself. Sending the access token as `refresh_token` is a real mistake to guard against: it fails silently (the exchange just gets rejected) rather than throwing something obviously wrong.

## The unified `token()` exchange

`login()` and `refreshToken()` are both thin wrappers around `token()`, which accepts either grant type directly - useful if you're building your own auth flow on top:

```typescript
await kerne.auth.token({ grant_type: 'password', email, password });
await kerne.auth.token({ grant_type: 'refresh_token', refresh_token });
```

=== ./sdks/server/auth/verify-email.mdx ===
---
title: "Verify email"
description: "Verify and manage email verification status"
---

There are two verification flows - a 6-digit code, or a link - plus one legacy single-token method:

```typescript
// Send a verification email (code or link)
await kerne.auth.sendVerificationEmail('code'); // or 'link' - throttled client-side, 60s cooldown

// Verify with the 6-digit code
const { success, needsTokenRefresh } = await kerne.auth.verifyEmailWithCode('483920');

// Or verify with the link's token (public route, no session needed)
await kerne.auth.verifyEmailWithLink(tokenFromLink);

// Check current status
const { emailVerified, needsVerification, email } = await kerne.auth.getVerificationStatus();
```

<Note>
`needsTokenRefresh: true` means the access token's `email_verified` claim is now stale - call [`refreshToken()`](/sdks/server/auth/refresh-token) to get one that reflects the new status.
</Note>

## Legacy single-token verify

```typescript
await kerne.auth.verifyEmail(tokenFromEmail);
```

Prefer the code/link flow above for new integrations - this is the older, simpler variant kept for compatibility.

=== ./sdks/server/admin/overrides.mdx ===
---
title: "Overrides"
description: "grant / listGrants / revokeGrant"
---

An entitlement override replaces a scope's **limit** for a feature - "this customer has a 1,000/mo deal" - and renews every period exactly like the plan's own limit would, until it expires (or forever, if you don't set an expiry). It has no effect on period boundaries, resets, or rollover - only the limit itself.

```typescript
// Grant - creates one, or updates it if this scope+feature already has one
await kerne.admin.grant('api_calls', {
  scope: userId,
  value: '50000',           // same encoding as a normal entitlement value
  reason: 'Annual contract - negotiated limit',
  expiresAt: '2027-01-01T00:00:00.000Z', // omit for permanent
});

// List
const grants = await kerne.admin.listGrants();          // every override in the tenant
const forUser = await kerne.admin.listGrants(userId);   // just this scope

// Revoke
await kerne.admin.revokeGrant(overrideId);
```

Each entry includes `is_expired` - an expired override still shows up in the list (for audit history), it's just no longer applied. `overage`/`overage_rate` are never overridden this way - they're always read from the plan's own entitlement definition.

For a one-off credit instead of a standing deal, use [`adjustUsage()`](/sdks/server/admin/usage-corrections) - it touches the counter, not the limit.

=== ./sdks/server/admin/usage-corrections.mdx ===
---
title: "Usage corrections"
description: "setUsage / adjustUsage / resetUsage"
---

<Note>
Everything under `kerne.admin` requires an admin caller (secret key, or a JWT owner crossing into their own tenant) - never call these from a request an end user initiated themselves.
</Note>

## `adjustUsage()` - the one to reach for

Offsets the counter by a signed delta in **one atomic increment** - safe to call concurrently with `consume()`/`reportUsage()` without racing them, because it never reads the current value first.

```typescript
// Refund 5 units back to the scope
await kerne.admin.adjustUsage('api_calls', { scope: userId, delta: -5 });

// Correct an undercount
await kerne.admin.adjustUsage('api_calls', { scope: userId, delta: 3, idempotencyKey: fixId });
```

A negative delta can push the counter below zero internally - that's correct (it's real slack the scope has), and [`check()`](/sdks/server/entitlements/allows-enforce-check) never surfaces it as a negative number, it folds the credit into the displayed limit instead.

## `setUsage()` - only when you need an exact value

```typescript
await kerne.admin.setUsage('storage_gb', { scope: userId, value: 12.5 });
```

Requires knowing the target absolute value up front, which means it can race a concurrent `consume()`/`reportUsage()` (read-then-write). Prefer `adjustUsage()` unless you specifically need to pin an exact number.

## `resetUsage()`

```typescript
await kerne.admin.resetUsage({ scope: userId }); // every QUOTA feature for this scope
await kerne.admin.resetUsage({ scope: userId, featureKey: 'api_calls' }); // just one
```

Zeroes both the current period's counter and any rollover credit/debt - a clean slate, not just "back to zero for this period."

## This is not the same as an override

These three change the **counter**. An [entitlement override](/sdks/server/admin/overrides) changes the **limit** and renews every period. See [Entitlements](/concepts/monetization/entitlements#two-ways-an-admin-can-deviate-from-the-plan) for when to use which.

=== ./sdks/server/entitlements/report-usage.mdx ===
---
title: "reportUsage()"
description: "Record usage without checking a limit"
---

Unlike [`consume()`](/sdks/server/entitlements/consume), `reportUsage()` never blocks on the limit - it always applies. Use it when the thing you're gating was already allowed some other way (e.g. a background job re-syncing usage counts, or metering something after the fact rather than at the moment of use).

```typescript
await kerne.reportUsage('storage_gb', {
  scope: userId,
  delta: 2.5,
  operation: 'INCREMENT', // or 'SET' to replace the value outright
  idempotencyKey: syncJobId,
});
```

<ParamField path="scope" type="string" required>
  Required here (unlike `consume()`/`check()`) - there's no self-fallback for this one, you always name a scope.
</ParamField>
<ParamField path="delta" type="number">
  Defaults to `1`.
</ParamField>
<ParamField path="operation" type="'INCREMENT' | 'SET'">
  Defaults to `INCREMENT`.
</ParamField>
<ParamField path="idempotencyKey" type="string">
  Same replay-safety as `consume()`.
</ParamField>
<ParamField path="metadata" type="object">
  Arbitrary context stored alongside the usage event (e.g. `request_id`).
</ParamField>

=== ./sdks/server/entitlements/consume.mdx ===
---
title: "consume()"
description: "Atomically check a quota and commit the usage in one step"
---

Use `consume()` instead of `check()` when the action you're gating **is** the usage - the limit check and the increment happen in one atomic database statement, so two concurrent requests can't both slip through a `BLOCK` limit the way a separate check-then-increment would allow.

```typescript
const result = await kerne.consume('api_calls', {
  scope: userId,
  delta: 1,              // defaults to 1
  idempotencyKey: requestId, // optional - see below
});
// { allowed, limit, used, remaining, overage_behavior, ... }
```

If `allowed` is `false`, nothing was incremented - the request never happened as far as the counter is concerned.

## Idempotency

Pass a stable `idempotencyKey` (e.g. your own request id) and a retried call with the same key replays the original decision instead of double-counting - safe to retry on a timeout without double-charging usage.

```typescript
await kerne.consume('api_calls', { scope: userId, idempotencyKey: `req_${requestId}` });
```

## Only for QUOTA features

`consume()` throws if called on a BOOLEAN or STATIC feature - those have nothing to increment. Use [`allows()`/`check()`](/sdks/server/entitlements/allows-enforce-check) for those instead.

=== ./sdks/server/entitlements/allows-enforce-check.mdx ===
---
title: "allows() / enforce() / check()"
sidebarTitle: "Check an entitlement"
description: "The three ways to ask 'is this scope allowed to do that'"
---

All three resolve the exact same entitlement - they only differ in what they hand back. Pick based on what you're about to do with the answer.

```typescript
// UI conditional, or any branch where a plain boolean is enough
const canExport = await kerne.allows('export_pdf', { scope: userId });

// Guard/middleware - let it throw instead of checking a boolean yourself
await kerne.enforce('export_pdf', { scope: userId });

// You need the detail (a quota's limit/used/remaining), not just yes/no
const result = await kerne.check('api_calls', { scope: userId });
// { allowed, feature_key, feature_type, limit, used, remaining, overage_behavior, has_override, ... }
```

## Parameters

<ParamField path="featureKey" type="string" required>
  The feature's key, as configured in the dashboard.
</ParamField>
<ParamField path="scope" type="string">
  Whose entitlement to check. With a secret key there's no "current user" - you must pass this explicitly (it's the id you used as `scope_id` when the subscription was created).
</ParamField>
<ParamField path="requested" type="number">
  For quota features: "can this scope use `requested` more units?" - defaults to `1`.
</ParamField>

## `enforce()` throws a plain `Error`

Not a typed `KerneError`, and not tied to an API error code - it's a client-side convenience for guard code, not something the server ever actually returns. Catch it yourself:

```typescript
try {
  await kerne.enforce('export_pdf', { scope: userId });
} catch {
  return res.status(403).json({ error: 'Upgrade required' });
}
```

## Reading the result of `check()`

Never negative, even when the scope is carrying a credit (a rollover or an [admin adjustment](/sdks/server/admin/usage-corrections)) - a credit is folded into `limit` instead of making `used` negative. See [Entitlements](/concepts/monetization/entitlements) for the full type breakdown (boolean/quota/static) and what each field means per type.

```typescript
const { url } = await kerne.billing.checkout(planPriceId, {
```

## Billing portal

A hosted page (Stripe/Polar) where the caller manages their own payment method, invoices, and plan - for the caller's own identity, same as [checkout](/sdks/server/billing/checkout).

```typescript
const { url } = await kerne.billing.portal({ returnUrl: 'https://app.example.com/settings' });
```

## Cancel

```typescript
// Cancel the caller's own active subscription
await kerne.billing.cancel({ immediately: false }); // false = at period end (default)

// Cancel a specific subscription (admin, any scope)
await kerne.billing.subscriptions.cancel(subscriptionId, /* immediately */ true);
```

`immediately: false` keeps access through the current period's end - the common choice, since an abrupt cutoff mid-period is rarely what you want for a self-service cancel.

title: "Overview"

`@kerne/react` manages session state (login, token refresh) and gives you hooks/components to gate UI on entitlements - it never holds a secret key, and never touches the catalog.

## Installation

```bash
npm install @kerne/react
```

## Initialization

```tsx
import { KerneProvider } from '@kerne/react';

function Root() {
  return (
    <KerneProvider appId={process.env.NEXT_PUBLIC_KERNE_APP_ID!}>
      <App />
    </KerneProvider>
  );
}
```

`KerneProvider` only ever takes `appId` - never a secret key. Session refresh is automatic (`autoRefresh`, default `true`) - see [Session](/sdks/client/react/auth/session).

## Core hooks

- **`useAuth()`** - the logged-in user, and every auth action (login/register/logout/password/verification). See [Login](/sdks/client/react/auth/login).
- **`useAllows(featureKey)`** - `{ allowed, isLoading, error }` for one feature, already scoped to the logged-in user (no need to pass one). See [Check an entitlement](/sdks/client/react/billing/check-entitlement).
- **`useCheck(featureKey)`** - the full entitlement detail (`limit`/`used`/`remaining`/`overage_behavior`) instead of a plain boolean - for UI that shows *how much* is left, not just yes/no.
- **`useCheckout()`** / **`usePortal()`** - start a checkout session, or open the billing portal. See [Checkout & portal](/sdks/client/react/billing/checkout-and-portal).
- **`useSubscription()`** / **`useUser()`** - reactive reads of the caller's own subscription/profile.
- **`useClient()`** - the underlying `KerneClient` instance, for anything not covered by the hooks above.

## Gating a feature

The guard components (`<Allows>`, `<Authenticated>`, `<Protected>`, ...) wrap the same hooks so you don't hand-roll loading/error state yourself - see [Guard components](/sdks/client/react/components):

```tsx
import { Allows } from '@kerne/react';

function ExportButton() {
  return (
    <Allows feature="export_pdf" fallback={<p>Upgrade your plan to use this.</p>}>
      <button>Export Data</button>
    </Allows>
  );
}
```

## What this SDK does not do

There's no `consume()` here on purpose - a quota check enforced only in the browser is trivially bypassed. Commit usage from your backend (`@kerne/server`'s [`consume()`](/sdks/server/entitlements/consume)), and use this SDK only to reflect the result in your UI.

=== ./sdks/client/react/billing/check-entitlement.mdx ===
---
title: "Check an entitlement"
description: "useAllows/useCheck and <Allows> - all scoped to the logged-in user automatically"
---

Unlike the server SDK, there's no `scope` parameter here - the client always checks the currently authenticated user, resolved from their own session.

## The hook

```tsx
import { useAllows } from '@kerne/react';

function ExportButton() {
  const { allowed, isLoading } = useAllows('export_pdf');

  if (isLoading) return <Spinner />;
  if (!allowed) return <UpgradePrompt />;
  return <button onClick={exportPdf}>Export</button>;
}
```

For a quota feature, pass `requested` to check "can I use N more":

```tsx
const { allowed } = useAllows('api_calls', 5);
```

Need more than yes/no - how much of the quota is left, for example - use `useCheck` instead, it returns the full entitlement detail:

```tsx
import { useCheck } from '@kerne/react';

function ApiCallsMeter() {
  const { check, isLoading } = useCheck('api_calls');

  if (isLoading || !check) return <Spinner />;
  return <p>{check.remaining} / {check.limit} calls left this period</p>;
}
```

## The guard component

`<Allows>` wraps `useAllows` for declarative gating:

```tsx
import { Allows } from '@kerne/react';

<Allows feature="export_pdf" fallback={<UpgradePrompt />}>
  <button onClick={exportPdf}>Export</button>
</Allows>
```

## Lower-level: `useClient().allows()` / `.check()`

Both hooks above call these internally on the underlying `KerneClient` - reach for them directly only if you need to trigger a check imperatively (e.g. on a button click, not on mount):

```tsx
import { useClient } from '@kerne/react';

const client = useClient();
const allowed = await client.allows('export_pdf'); // boolean, throws on a real error (401/500) - it does not swallow failures into `false`
const check = await client.check('export_pdf'); // full EntitlementCheck detail
```

## Why there's no `consume()` here

Enforcing a quota only in the browser is trivially bypassed - commit usage from your backend with `@kerne/server`'s [`consume()`](/sdks/server/entitlements/consume), and use this SDK only to reflect the result.

## What is Kerne?

Kerne unifies authentication and billing into one API. Instead of stitching together an auth provider, Stripe, and your own quota-tracking code, you get one model: a user, a plan, and the entitlements that plan grants.

Every request your app makes boils down to the same question:

```
User wants to do X  →  kerne.allows('X')  →  Kerne decides  →  allowed: your app does X
                                                              →  denied: your app shows an upgrade prompt
```

That one call - `allows()` - is what replaces scattered `if (user.plan === 'pro')` checks across your codebase.

Building an invite-only application is a good way to control growth and validate your product with high-quality users.

<Steps>
  <Step title="Turn on invite-only mode">
    In the dashboard, enable `require_invitation`. This is enforced at the API level - even a request that bypasses your frontend entirely still needs a valid token or code.
  </Step>
  <Step title="Create codes/tokens (server-side)">

    ```typescript
    import { Kerne } from '@kerne/server';
    const kerne = new Kerne({ appId, secretKey });

    const { code, expiresAt } = await kerne.invitations.createCode({
      expiresAt: '2026-12-31T23:59:59.000Z', // omit for no expiry

    const { token } = await kerne.invitations.createToken({ email: 'alice@company.com' });
    ```

    Codes are server-generated, not something you pick yourself - there's no `code`/`maxUsages` field to set on creation.
  </Step>

    ```tsx

            password: data.password,
    ```

    You can validate a code up front (before showing the rest of the signup form) with `kerne.invitations.validateCode(code)` - a public route, no auth required.

## Pitfalls to avoid

**"Account already exists."** If someone with an invite code already has an account, `K1008` (email taken) is what you'll see - route that to "log in instead", not a generic failure message.

**Lost invites.** There's no `resend()` method today - re-sending means creating a new token/code and emailing it yourself. Track which emails you've already invited so you don't accidentally issue duplicates.

=== ./guides/auth/choose-your-auth-model.mdx ===
---
title: "Choose your auth model"
description: "Open, waitlist, or invite-only - and what Kerne doesn't have yet"
---

Your registration mode is one of the first decisions to make, and it's controlled by two flags read from `GET /v1/auth/config` - see [Registration modes](/concepts/identity/registration-modes) for the exact logic.

## Recommendation

<CardGroup cols={2}>
  <Card title="Consumer / self-serve" icon="users">
    Open registration (`allow_registration: true`, `require_invitation: false`). Friction is the enemy - every extra step loses signups.
  </Card>
  <Card title="Early access / high-touch onboarding" icon="building">
    Invite-only (`require_invitation: true`) or a waitlist first. Fewer, more qualified signups, and room to onboard people by hand while you're still learning what they need.
  </Card>
</CardGroup>

## Setting it

Registration mode is tenant *configuration* - the rules your SaaS runs under - not something a running request should be able to flip. Kerne keeps that distinction sharp on purpose: you set it once, in the dashboard, and every runtime SDK call (`kerne.auth.signup()`, `kerne.auth.config()`) simply operates under whatever rule is currently in force. That's why there's no `kerne.settings.update()` next to `signup()` - mixing "define the rules" and "apply the rules" into the same surface is exactly what makes a SaaS's auth config accidentally mutable from application code.

## What Kerne doesn't have (yet) that might change your plan

Be honest with yourself about these before committing to a model - working around a missing feature is more expensive than knowing upfront it isn't there:

- **No organizations/teams.** Every scope is one user - there's no "colleague joins the same workspace" concept. If your product is inherently collaborative (shared workspace, seats, team billing), that's not built yet.
- **No SSO/MFA.** Email+password and a passwordless-start flow (see [Identity overview](/concepts/identity)) - nothing enterprise-auth yet.
- **No OAuth/social login.** Only credential-based auth.

If any of those are load-bearing for your launch, it's worth knowing now rather than after building against Kerne.

    See [Registration modes](/concepts/identity/registration-modes).
  </Step>

  <Step title="Stage 2: Private beta">
    You have something worth trying, but not worth a public signup button yet - you want to control exactly who gets in and in what order.

    <Info>
    **Goal:** admit a small, chosen cohort (a launch list, people who asked first) without opening the doors.

    **Kerne strategy:** switch to invite-only. Generate codes for specific cohorts, and admit waitlist entries by hand as you're ready for them - see [Implement invite-only SaaS](/guides/auth/implement-invite-only-saas).
    </Info>
  </Step>

  <Step title="Stage 3: Self-serve">
    The product is ready for anyone to sign up and pay without you in the loop.

    <Info>
    **Goal:** let strangers subscribe and start using premium features immediately, with zero manual steps on your end.

    **Kerne strategy:** open registration, set up plans and checkout (see [Subscription setup](/guides/getting-started/subscription-setup)), and gate premium features by entitlement, not by plan name - a plan can be renamed or restructured later without breaking every check.
    </Info>

    ```tsx
    import { Allows } from '@kerne/react';

    <Allows feature="advanced_analytics" fallback={<UpgradePrompt />}>
      <AnalyticsDashboard />
    </Allows>
    ```
  </Step>

  <Step title="Stage 4: Negotiated deals">
    A customer wants terms that don't match any plan you sell publicly - a bigger limit, a custom discount, a handshake deal.

    <Info>
    **Goal:** give one customer a non-standard limit without inventing a one-off plan just for them.

    **Kerne strategy:** use an [entitlement override](/sdks/server/admin/overrides) (`kerne.admin.grant()`) - it's the same mechanism as a normal plan limit, just scoped to that one customer instead of everyone on a plan.
    </Info>

    Not built yet if you need it at this stage: SSO, multi-user organizations, and a first-class "enterprise contract" object - see [Platform foundations](/concepts/overview) for the current boundary.
  </Step>
</Steps>

---
title: "Checking entitlements"
sidebarTitle: "Entitlements"
description: "Gate features based on a user's subscription"
---

This guide shows the standard pattern for gating a feature - see [Entitlements](/concepts/monetization/entitlements) for the underlying model (the three types, and `allows()`/`enforce()`/`check()`/`consume()`).

## Server-side (the check that actually matters)

`userId` here is whatever you used as `scope_id` when the user's subscription was created - typically your own database id for that user, read from the authenticated request (a session, a JWT, whatever your app already uses):

```typescript
// e.g. an Express/Next.js route handler
async function exportReport(req, res) {
  const userId = req.user.id; // from your own auth middleware, not Kerne's

  if (!(await kerne.allows('advanced_analytics', { scope: userId }))) {
    return res.status(403).json({ error: 'Upgrade required to export reports.' });
  }

  const report = await generateReport(userId);
  return res.json(report);
}
```

A denial isn't just "don't run the code" - decide what the caller actually sees. For an API route, a `403` with a machine-readable reason your frontend can act on (as above) works better than a generic 500. For a page render, redirect to your pricing/upgrade page instead of rendering a broken state.

Acting on behalf of a specific request's user, rather than your own backend identity? Scope the client to their token first:

```typescript
const kerneAsUser = kerne.withToken(userAccessToken);
const canConsume = await kerneAsUser.allows('api_calls', { requested: 1 });
```

## Client-side (for UI, not security)

```tsx
import { Allows } from '@kerne/react';

<Allows feature="advanced_analytics" fallback={<UpgradeBanner />}>
  <AnalyticsDashboard />
</Allows>
```

`<Allows>` (and the `useAllows` hook underneath it) already handles the loading state and scopes to the logged-in user - no need to hand-roll a `useEffect`/`useState` wrapper around `client.allows()` yourself.

<Warning>
A client-side check is a UX convenience, never a security boundary - anyone can bypass it by editing the page. Always re-check with `allows()`/`enforce()` on the server before doing the thing being gated.
</Warning>

## Checking quotas

```typescript
const { entitlements } = await kerne.entitlements({ scope: userId });
const apiCalls = entitlements.find((e) => e.feature_key === 'api_calls');
console.log(`Used: ${apiCalls?.used} / ${apiCalls?.limit}`);
```

## Feature key patterns

| Key | Type | Description |
|-----|------|-------------|
| `api_access` | Boolean | Can use the API at all |
| `api_calls` | Quota | Monthly API call limit |
| `team_seats` | Static | Number of team members |
| `advanced_analytics` | Boolean | Access to pro analytics |

=== ./guides/billing/designing-pricing.mdx ===
---
title: "Designing your pricing"
description: "From simple subscriptions to usage-based models"
---

A well-designed pricing model is scalable, easy to understand, and maps directly to your code. Kerne allows you to iterate on pricing without rewriting your application logic.

## The core concepts

1.  **Entitlements (Features)**: What the user *gets* (e.g., "Can export PDF").
2.  **Plans (Tiers)**: A bundle of entitlements (e.g., "Pro Plan").
3.  **Prices (Billing)**: How much they pay for the plan (e.g., "$29/mo").

<Tip>
**Golden Rule**: Your code should check **entitlements**, never plans.
*   **Bad**: `if (user.plan === 'pro')`
*   **Good**: `if (await kerne.allows('export_pdf', { scope: userId }))`
</Tip>

## Model 1: The "Good-Better-Best" (Flat Rate)

This is the standard SaaS model.
- **Free**: Limited features.
- **Pro**: All features.

**Implementation**:
1.  Create features: `can_access_dashboard`, `can_invite_members`.
2.  Create plans:
    - **Free Plan**: Includes `can_access_dashboard`.
    - **Pro Plan**: Includes `can_access_dashboard` + `can_invite_members`.

## Model 2: The "Pay-as-you-go" (Usage Based)

Charge based on consumption (e.g., API calls, emails sent).

**Implementation**:
1.  Create a feature `emails_sent` with type **Quota**.
2.  Set the **Reset Policy**:
    - `RESET`: Counter resets every month (e.g., "1000 emails/mo included").
    - `ACCUMULATE`: Credits roll over (e.g., "Pre-paid email credits").
3.  Report usage via the SDK:
    ```typescript
    await kerne.reportUsage('emails_sent', { scope: userId, delta: 1 });
    ```

## Model 3: Hybrid (base plan + metered add-on)

A flat monthly fee plus a per-unit metered feature - e.g. $20/mo base, then $0.01/email past what's included. Model it as one plan with two entitlements: a boolean/static one for the base tier, and a `QUOTA` one (with `overage: ALLOW`) for the metered part - see [Entitlements](/concepts/monetization/entitlements) for how `overage_behavior` works. Kerne doesn't bill the overage automatically yet (see [Enforcing limits](/guides/billing/enforcing-limits-without-breaking-ux)) - you'd read `used` past `limit` and invoice for it separately, or via your payment provider's usage-based pricing feature directly.

=== ./guides/billing/enforcing-limits-without-breaking-ux.mdx ===
---
title: "Enforcing limits"
description: "Soft limits vs Hard limits and UX best practices"
---

Enforcing billing limits is a delicate balance between protecting your infrastructure and providing a friction-free experience for your customers.

## Soft vs. hard limits

### Hard limits

A hard limit (the "wall") blocks the user's action immediately upon hitting a threshold.
- **Example**: "You have reached your 5 team member limit. Upgrade to add more."
- **Use for**: Team seats, database storage, or expensive infrastructure resources.

### Soft limits

A soft limit (the "nudge") allows the user to proceed but triggers a notification or overage charge.
- **Example**: "You have exceeded 10,000 monthly views. We will charge $5 for the next 1,000."
- **Use for**: Bandwidth, email sends, or usage-based metrics.

## Where to enforce

### 1. Backend middleware (hard limits)

The safest place to enforce limits is your API layer - use `enforce()` if a thrown error fits your middleware pattern, or `allows()` if you'd rather branch yourself:

```typescript
if (!(await kerne.allows('api_calls', { scope: userId }))) {
  throw new ForbiddenError('You have reached your monthly API quota.');
}
```

If the action *is* the usage being counted, use [`consume()`](/sdks/server/entitlements/consume) instead - it checks and increments atomically, so it doesn't just check but also protects against a burst of concurrent requests all sneaking past the limit at once.

### 2. The client UI (soft limits and UX)

Don't wait for a "Save" click to inform users they've hit a limit - proactively disable buttons or show upgrade nudges, using [`useAllows`](/sdks/client/react/billing/check-entitlement) (which already handles the loading state):

```tsx
import { useAllows } from '@kerne/react';

function AddTeamMember() {
  const { allowed, isLoading } = useAllows('team_seats');

  return (
    <button disabled={isLoading || !allowed}>
      Add member {!isLoading && !allowed && ' (Upgrade required)'}
    </button>
  );
}
```

## Preventing "rage quit"

Nothing drives churn faster than losing data due to a billing limit.
- **Scenario**: A user spends 30 minutes writing a report, only to be blocked when clicking "Save".
- **Bad**: "Error: Storage limit reached." (User loses their work).
- **Good**: "Draft saved locally. You've reached your storage limit—upgrade your plan to publish this report."

Always check limits **before** the user begins a resource-intensive task.

=== ./concepts/overview.mdx ===
---
title: "Overview"
description: "The mental model behind Kerne"
---

Kerne answers one question, asked on every request: **does this scope have the right to do that, right now, given what it pays?**

```
Scope wants an action  →  kerne.allows() / enforce() / check()
                       →  Kerne resolves: subscription → pack → entitlement → override
                       →  Your app reacts: proceed, or show an upgrade prompt
```

Everything else in the platform exists to make that one decision correct and fast.

## The two halves of the model

**Identity** - who is making the request. A user signs up, logs in, and holds a session. See [Identity & access](/concepts/identity).

**Monetization** - what that user is entitled to. A user subscribes to a `Plan`, which pins a versioned `Pack` (a snapshot of feature entitlements, frozen at subscription time) - see [Monetization](/concepts/monetization).

A **scope** is whoever the entitlement belongs to. Today that's always a single user - in API terms, `scope_type` is always `"USER"`. Organization/team scopes aren't built yet - see below.

## What exists today

<AccordionGroup>
  <Accordion title="Identity">
    Email/password and magic-link-style sessions, invitation-gated or open registration, a waitlist.
  </Accordion>
  <Accordion title="Catalog & entitlements">
    Products, plans versioned via packs - so upgrading a plan's entitlements never silently changes what existing subscribers get, see [grandfathering](/concepts/monetization/products-and-plans) - and three entitlement types: boolean flags, numeric quotas, and static config values.
  </Accordion>
  <Accordion title="Payments">
    Stripe and Polar as payment rails. Kerne is always the source of truth for entitlements; the provider only handles money movement.
  </Accordion>
  <Accordion title="Admin">
    A single admin flag per user (`global_role`), not a permissions system.
  </Accordion>
</AccordionGroup>

## What's intentionally not built yet

Being explicit about this matters more than it sounds - a doc that describes a half-built feature as if it were finished costs you more trust than one that says "not yet."

<AccordionGroup>
  <Accordion title="Organizations / teams">
    Every scope is a single user. A workspace shared by multiple people, with pooled or per-member quotas, isn't implemented.
  </Accordion>
  <Accordion title="Role-based access control">
    There's no permission system beyond one admin/non-admin flag - no custom roles, no per-resource permissions.
  </Accordion>
  <Accordion title="OAuth / social login">
    Only email+password and magic-link-style flows exist.
  </Accordion>
</AccordionGroup>

If your product needs any of these today, it's worth knowing before you build against Kerne - not after.

=== ./concepts/identity/registration-modes.mdx ===
---
title: "Registration modes"
description: "Controlling who can sign up"
---

Whether `kerne.auth.signup()` succeeds depends on three settings, read from `GET /v1/auth/config` (`kerne.auth.config()`) and checked in this order:

1. **User limit.** If `user_registration_limit` is set and the tenant already has that many active users, every signup is rejected - regardless of the other two settings.
2. **Open registration.** If `allow_registration` is `true` and `require_invitation` is `false`, any signup succeeds.
3. **Invite-only.** If `require_invitation` is `true`, the signup must include a valid `invitationToken` or `invitationCode` (see [Invitations](/sdks/server/invitations/create)) - anything else is rejected.

If neither open registration nor an invitation applies, registration is closed.

## Waitlist vs. invitations

These are two separate mechanisms - joining a waitlist does not grant registration access by itself, and doesn't put a user into any kind of pending account state:

- **Waitlist** (`kerne.waitlist.join()`) just collects interest before you're ready to onboard everyone - an email and optional metadata, nothing more. An admin later invites specific entries, at which point they go through the same invitation flow as anyone else.
- **Invitations** (tokens or reusable codes, `kerne.invitations.*`) are what actually unlock a signup when `require_invitation` is `true`.

## Checking the current config

```typescript
const config = await kerne.auth.config();
// { allow_registration, require_invitation, enable_magic_link,
//   enable_credentials, oauth_providers, callback_url,
//   user_registration_limit, app_name }
```

Use this to render the right signup form client-side (e.g. hide the password field if `enable_credentials` is `false`) instead of hardcoding assumptions about how your tenant is configured. Note `enable_magic_link` and `oauth_providers` currently describe intent more than working flows - see [Identity overview](/concepts/identity) for what's actually wired up.

For a walkthrough of building an invite-only product end to end, see [Implement invite-only SaaS](/guides/auth/implement-invite-only-saas).

Identity in Kerne separates two questions: **who is this** (authentication) and **what have they paid for** (entitlements - see [Monetization](/concepts/monetization)).

## Authentication

Kerne supports:
- **Email and password** - the standard flow, via `kerne.auth.signup()` / `kerne.auth.login()`.
- **Passwordless start** - `kerne.auth.startPasswordless(email)` sends a one-time link. The verification side of this flow isn't wired up yet - don't build a "magic link login" UI against it today.

Not supported: social/OAuth login (Google, GitHub, etc.) - there's no provider integration, despite `AuthConfig.oauth_providers` existing as a field in the config response (it's always empty today).

Every successful signup/login returns a JWT access token plus a refresh token (`kerne.auth.token()`, or the higher-level `signup()`/`login()`). See [Registration modes](/concepts/identity/registration-modes) for how a tenant controls *who* is allowed to sign up.

## Authorization

There's a single flag: a user's `global_role` is either `USER` or `ADMIN`. That's it - no custom roles, no per-resource permissions, no organizations. See [Authorization](/concepts/identity/authorization) for exactly what that flag does and doesn't gate.

## Entitlements

Entitlements answer "what has this user paid for" and are covered in full in [Monetization](/concepts/monetization) - they're a separate axis from authorization. A user can be `ADMIN` and still be on a free plan with no `advanced_analytics` entitlement.

=== ./concepts/identity/authorization.mdx ===
---
title: "Authorization"
description: "What global_role actually gates today"
---

<Note>
There's no permission system here yet - this page describes one boolean flag, not a roles/permissions engine. If you need custom roles or per-resource permissions, that's not built.
</Note>

Every user has a `global_role`: `USER` or `ADMIN`. It exists for one purpose - letting *you* (the tenant) build your own admin dashboard on top of Kerne's API, by giving certain of your users elevated API access (list/manage other users, correct usage, grant overrides). It is **not** a system for managing collaborators on Kerne itself - there's no concept yet of inviting a teammate to help manage your Kerne tenant.

## What `ADMIN` unlocks

Routes gated `@RequireAdmin()` server-side accept two kinds of caller: your secret key, or a JWT belonging to a user whose `global_role` is `ADMIN`. That covers things like:

- Listing/managing other users (`GET/PATCH /v1/users/:id` for someone other than yourself)
- Usage corrections (`kerne.admin.setUsage/adjustUsage/resetUsage`)
- Entitlement overrides (`kerne.admin.grant/revokeGrant`)
- Waitlist and invitation management

A plain `USER` can only ever act on their own scope (their own profile, their own entitlements, their own usage).

## Setting it

```typescript
await kerne.users.update(userId, { /* ... */ });
```

`global_role` isn't settable through the self-service `users.update()` params today - promoting a user to `ADMIN` is a tenant-configuration action, done through the dashboard or the control-plane API, not something a plain end-user request can do to itself (the server strips `global_role` from the update body unless the caller is already an admin).

=== ./concepts/error-codes.mdx ===
---
title: "Error codes"
description: "Standardized error responses for the Kerne API"
---

Every error response follows this shape - there's no `{success, data}` envelope on success responses either, they return the resource directly:

```json
{
  "error": {
    "type": "AUTH_ERROR",
    "code": "K1005",
    "message": "Invalid email or password",
    "statusCode": 401,
    "details": {}
  }
}
```

`@kerne/server` throws a typed `KerneError` (or a subclass - `AuthenticationError`, `AuthorizationError`, `NotFoundError`, `ValidationError`, `RateLimitError`) built from this shape, so you can `instanceof` it instead of parsing `code` yourself.

## Auth and registration (K1xxx)

| Code | Description |
|------|-------------|
| `K1001` | Registration is currently disabled for this app. |
| `K1002` | Maximum user limit reached. |
| `K1003` | Invalid, expired, or already-used invitation token. |
| `K1004` | Invalid, expired, or already-used invitation code. |
| `K1005` | Invalid email or password. |
| `K1006` | Token has expired. |
| `K1007` | No token provided. |

description: "Decoupling pricing from code"
---

Without Kerne, billing logic tends to leak into scattered checks across your codebase:

```typescript
if (user.plan === 'pro') {
  showAdvancedAnalytics();
}
```

Change the packaging - move "Advanced Analytics" to a new "Enterprise" tier - and you have to hunt down every one of those checks and redeploy.

## The Kerne approach

Plans grant **entitlements**, defined once in the dashboard (which feature, and what limit). Your code only ever asks about the feature, never the plan:

```typescript
if (await kerne.allows('advanced_analytics', { scope: user.id })) {
  showAdvancedAnalytics();
}
```

Reassign that feature to a different plan in the dashboard, and this line of code doesn't change - `allows()` resolves it dynamically every time.

## The pieces

- **[Products & plans](/concepts/monetization/products-and-plans)** - what you sell, and how a plan's entitlements are versioned so changing a plan never silently changes what existing subscribers get.
- **[Entitlements](/concepts/monetization/entitlements)** - the three entitlement types (boolean, quota, static) and how overrides/usage corrections work.

=== ./concepts/monetization/entitlements.mdx ===
---
title: "Entitlements"
description: "What a plan actually grants, and how it's checked"
---

An entitlement is one feature's value for one scope, resolved from whatever pack their subscription is pinned to (or overridden - see below). Every feature is one of three types.

## The three types

<Tabs>
  <Tab title="Boolean">
    An on/off switch. `kerne.check()` returns `{ allowed, enabled }`.

    ```typescript
    const { allowed } = await kerne.check('sso_enabled', { scope: userId });
    ```
  </Tab>
  <Tab title="Quota">
    A numeric limit with usage tracking - `limit`, `used`, `remaining`. Reset behavior is per-feature:
    - `RESET` - zeroes every period (classic "10,000 calls/month").
    - `ACCUMULATE` - unused quota rolls over as credit into the next period; overuse rolls over as debt.
    - `STATIC` - never resets, lifetime total (a one-time allowance).

    ```typescript
    const result = await kerne.consume('api_calls', { scope: userId, delta: 1 });
    // { allowed, limit, used, remaining, overage_behavior }
    ```

    `limit: null` means unlimited. When a limit is hit, `overage_behavior` decides what happens: `BLOCK` refuses further use, `ALLOW` lets it through (a soft limit you can bill for separately).
  </Tab>
  <Tab title="Static">
    A config value, not a limit - returned as-is (e.g. `support_level: "gold"`).

    ```typescript
    const { value } = await kerne.check('support_level', { scope: userId });
    ```
  </Tab>
</Tabs>

## `allows()` vs `enforce()` vs `check()`

All three resolve the same entitlement - they differ only in what they hand back:

| | Returns | Use it for |
|---|---|---|
| `allows()` | `boolean` | UI conditionals |
| `enforce()` | nothing, throws if denied | guards/middleware |
| `check()` | the full object (`limit`/`used`/`remaining`/...) | anywhere you need the detail, not just yes/no |

For quota features specifically, use `consume()` instead of `check()` when the action you're gating *is* the usage - it checks the limit and commits the increment in one atomic step, so two concurrent requests can't both slip through a `BLOCK` limit. `check()`/`allows()` never increment anything.

## Two ways an admin can deviate from the plan

These solve different problems - don't reach for one when you mean the other:

- **`kerne.admin.grant()`** creates an override: a *replacement limit* that renews every period just like the plan's own limit, until it expires (or forever). This is "this customer has a 1,000/mo deal," not a one-time gift.
- **`kerne.admin.adjustUsage()`** offsets the usage counter by a signed delta, once. This is "credit this customer 500 units back," and has no effect on their limit going forward.

## Errors

`allows()`/`check()`/`consume()` never throw for a denial - a denied request comes back as `{ allowed: false, ... }`, a normal (200) response. `enforce()` is the one that throws, and it's a plain `Error` you catch yourself - not tied to an API error code. See [Enforcing limits without breaking UX](/guides/billing/enforcing-limits-without-breaking-ux) for handling a denial gracefully instead of a hard failure.

title: "Products, plans, and packs"
description: "Designing your pricing model, and why grandfathering is automatic"
---

## The hierarchy

```
Product  →  Plan  →  PlanPrice        (what you sell, and how you charge for it)
              │
              └──→  Pack (versioned)   →  entitlements per feature
```

- **Product** - your application or service line. Most SaaS apps have exactly one.
- **Plan** - a tier ("Free", "Pro", "Enterprise"). Maps loosely to a Stripe/Polar product.
- **PlanPrice** - a specific billing option for a plan (monthly, yearly, a specific currency). Maps to a Stripe/Polar price. A plan can have several.
- **Pack** - the actual set of feature entitlements attached to a plan, and the piece that makes grandfathering automatic (see below).

## Why Pack exists: grandfathering by default

When a subscriber signs up, their subscription pins the plan's **currently-active pack** - not a live reference to "whatever the Pro plan currently includes." If you later publish a new pack version for the Pro plan (raise a quota, add a feature), that change only applies to *new* subscribers. Everyone already on Pro keeps exactly what they signed up for, forever - until you explicitly migrate them.

This is deliberate, not a limitation: pricing changes are common, and "we silently changed what our existing customers pay for" is the kind of bug that erodes trust. Kerne makes the safe behavior (don't change existing subscribers) the default, and the unsafe one (migrate everyone immediately) something you do on purpose.

```
Pack v1 (ACTIVE until v2 ships) → Subscriber A pins v1 forever, even after v2 activates
Pack v2 (ACTIVE after publish)  → Subscriber B (signs up after) gets v2
```

## What you don't need to think about

Your application code never references a pack directly - `kerne.allows()`/`check()`/`entitlements()` all resolve through the subscriber's pinned pack automatically. Packs are configured once, in the dashboard, precisely so your runtime code never has to think about versioning - see [Entitlements](/concepts/monetization/entitlements) for the actual runtime check.

## Prerequisites

- Node.js 18 or later
- A Kerne app (`x-app-id`) and, for backend calls, a secret key (`sk_live_...` or `sk_test_...`)

## 1. Install the SDKs

<Tabs>
  <Tab title="npm">
    ```bash
    # For your backend
    npm install @kerne/server

    # For your React frontend
    npm install @kerne/react
    ```
  </Tab>
  <Tab title="pnpm">
    ```bash
    pnpm add @kerne/server @kerne/react
    ```
  </Tab>
</Tabs>

## 2. Backend setup

The server SDK is the only place that should ever hold your secret key - it's what lets you act on behalf of any user (create their subscription, correct their usage, grant an override).

```typescript
// src/lib/kerne.ts
import { Kerne } from '@kerne/server';

export const kerne = new Kerne({
  appId: process.env.KERNE_APP_ID!,
  secretKey: process.env.KERNE_SECRET_KEY!, // sk_live_...
});
```

## 3. Frontend setup

`KerneProvider` never takes a secret key - only `appId`. It manages the session (login state, token refresh) for you.

```tsx
// src/providers.tsx
import { KerneProvider } from '@kerne/react';

export function Providers({ children }: { children: React.ReactNode }) {
  return (
    <KerneProvider appId={process.env.NEXT_PUBLIC_KERNE_APP_ID!}>
      {children}
    </KerneProvider>
  );
}
```

## 4. Sign a user up and log them in

<CodeGroup>
```typescript Server
const { token, user } = await kerne.auth.signup({
  email: 'user@example.com',
  password: 'a-strong-password',
});
```

```tsx Client
import { useAuth } from '@kerne/react';

function LoginForm() {
  const { login } = useAuth();

  return (
    <button onClick={() => login({ email, password })}>
      Log in
    </button>
  );
}
```
</CodeGroup>

## 5. Gate a feature behind an entitlement

On the server, `scope` identifies *whose* entitlement you're checking - with a secret key there's no "current user", so you always pass it explicitly (it's whatever id you used as `scope_id` when creating the subscription, typically your own user id):

<CodeGroup>
```typescript Server
const canExport = await kerne.allows('export_pdf', { scope: user.id });

if (!canExport) {
  throw new Error('Upgrade required');
}
```

```tsx Client
import { Allows } from '@kerne/react';

function ExportButton() {
  return (
    <Allows feature="export_pdf" fallback={<UpgradePrompt />}>
      <button onClick={exportPdf}>Export as PDF</button>
    </Allows>
  );
}
```
</CodeGroup>

On the client, `Allows` (and the `useAllows` hook) check the *logged-in* user automatically - no scope needed, the SDK already knows who's authenticated.
