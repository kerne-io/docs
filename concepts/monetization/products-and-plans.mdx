## The hierarchy

```
Product  →  Plan  →  PlanPrice        (what you sell, and how you charge for it)
              │
              └──→  Pack (versioned)   →  entitlements per feature
```

- **Product** - your application or service line. Most SaaS apps have exactly one.
- **Plan** - a tier ("Free", "Pro", "Enterprise"). Maps loosely to a Stripe/Polar product.
- **PlanPrice** - a specific billing option for a plan (monthly, yearly, a specific currency). Maps to a Stripe/Polar price. A plan can have several.
- **Pack** - the actual set of feature entitlements attached to a plan, and the piece that makes grandfathering automatic (see below).

## Naming a plan's prices

Once a plan has more than one price, each one gets a **label** ("Monthly", "Annual", "Early bird") so a pricing page knows what to call it and which ones belong together across plans - "the annual price" is the same label on every plan, which is what lets a single toggle switch the whole page at once. Set it when you create the price in the dashboard; [`<PricingTable>`](/sdks/client/react/ui/pricing-table) reads it to build that toggle for you, including the "Save 20%" hint when an annual price is genuinely cheaper per month than the monthly one.

## Why Pack exists: grandfathering by default

When a subscriber signs up, their subscription pins the plan's **currently-active pack** - not a live reference to "whatever the Pro plan currently includes." If you later publish a new pack version for the Pro plan (raise a quota, add a feature), that change only applies to *new* subscribers. Everyone already on Pro keeps exactly what they signed up for, forever - until you explicitly migrate them.

This is deliberate, not a limitation: pricing changes are common, and "we silently changed what our existing customers pay for" is the kind of bug that erodes trust. Kerne makes the safe behavior (don't change existing subscribers) the default, and the unsafe one (migrate everyone immediately) something you do on purpose.

```
Pack v1 (ACTIVE until v2 ships) → Subscriber A pins v1 forever, even after v2 activates
Pack v2 (ACTIVE after publish)  → Subscriber B (signs up after) gets v2
```

## What you don't need to think about

Packs are created and versioned in the dashboard under **Catalog → Plans**.
Your application code never references a pack directly - `kerne.allows()`/`check()`/`entitlements()` all resolve through the subscriber's pinned pack automatically - see [Entitlements](/concepts/monetization/entitlements) for the actual runtime check.

## Billing lifecycle policy

A product also decides what happens at moments in a subscriber's life: canceling, and a failed payment.

<AccordionGroup>
  <Accordion title="On cancel">
    Always **end of period** by default - access continues through what's already been paid for, and only stops when that period actually ends. Calling `cancel()` (server SDK or `useCancelSubscription`) with `immediate: true` stops access right away instead. This is a per-call choice, not a stored setting.
  </Accordion>
  <Accordion title="On payment failure">
    **None** (default) - Kerne never automatically cuts access for a failed payment; the subscription sits at `PAST_DUE` until the provider resolves it (payment retried, or the provider cancels it). **Block, with a grace period** - after the first failed payment, the subscriber keeps access for `grace_period_days` more days (still `PAST_DUE`), and a background sweep then moves the subscription to `UNPAID` - which does cut access - if nothing was paid by then. Set once per product, on that product's page in the dashboard, below its pricing matrix.
  </Accordion>
</AccordionGroup>

`PAST_DUE` and `UNPAID` are subscription statuses - see the [subscription shape](/sdks/server/billing/subscription#shape) for the full list.

A downgrade (switching to a cheaper plan on an active subscription) always applies immediately today - there is no end-of-period option yet.
