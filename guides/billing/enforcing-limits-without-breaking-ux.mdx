A limit needs two checks: the real one on your backend, and one in your UI so the customer isn't surprised.

## Check on your backend

```typescript
async function exportReport(req, res) {
  const allowed = await kerne.allows('advanced_analytics', { customer: req.user.id });
  if (!allowed) return res.status(403).json({ error: 'upgrade_required' });

  return res.json(await generateReport(req.user.id));
}
```

Decide what a denial looks like. For an API route, a `403` with a reason your frontend can act on. For a page, a redirect to your pricing page.

When the action is the thing you count, use [`consume()`](/sdks/server/entitlements#consume-a-quota) instead. It checks and counts in one step, so a burst of requests can't all slip past the limit:

```typescript
const { allowed } = await kerne.consume('api_calls', { customer: req.user.id });
if (!allowed) return res.status(429).json({ error: 'quota_exceeded' });
```

`consume()` needs the customer to exist in Kerne. People who signed up through Kerne do, and a first checkout creates one. Otherwise, call [`kerne.customers.upsert()`](/sdks/server/overview#customers) once.

## Show it in your UI

```tsx
import { Access } from '@kerne/react';

<Access featureKey="advanced_analytics" fallback={<UpgradeBanner />}>
  <AnalyticsDashboard />
</Access>;
```

`<Access>` checks for the signed-in user and handles loading. It hides things, it doesn't protect them: anyone can edit a page, so the backend check is the one that counts.

Disable a control before someone hits the limit, not after they click:

```tsx
import { useAccess } from '@kerne/react';

function AddTeamMember() {
  const { allowed, isLoading } = useAccess('team_seats');
  return <button disabled={isLoading || !allowed}>Add member</button>;
}
```

## Stop, or keep serving?

What happens past the allowance is set on each plan, under **Past the allowance**: **Stop**, **Keep free** or **Bill it**. Your code stays the same.

**Stop** suits what a customer should decide to buy more of: seats, storage, expensive infrastructure. **Bill it** suits usage-shaped things, like email sends or bandwidth, where blocking angers a customer without protecting anything. See [Design your pricing](/guides/billing/designing-pricing).

A spending cap stops the billing, never the service. To stop usage, set a ceiling in units: see [why the cap doesn't block](/concepts/monetization/usage-billing#why-the-cap-doesnt-block).

## Don't lose the user's work

Someone who spends 30 minutes on a report and gets blocked on **Save** doesn't file a ticket: they leave. "Draft saved. Upgrade to publish" keeps their work, "Error: storage limit reached" throws it away. Check before the expensive step starts, not only when they submit.
