---
title: "Enforcing limits without breaking UX"
description: "Where a limit should stop a user, and where it should just start billing them"
---

A limit that blocks and a limit that bills are the same mechanism with a different `overage_behavior` - the judgment call is which one fits what you're limiting, not how to build either.

## Hard limits: block

A hard limit refuses the action once the allowance is gone - "You've reached your 5 team member limit. Upgrade to add more." Right for things a customer should decide to buy more of on purpose: team seats, database storage, expensive infrastructure. Nobody should discover they bought more of these as a surprise line on an invoice.

## Soft limits: keep going and bill

A soft limit lets the action through and charges for the excess instead - "You've used all 10,000 included views this month; the next ones are billed at $0.005 each." Right for bandwidth, email sends, anything usage-shaped where blocking would just make a customer angry instead of protecting anything. On the plan, choose to keep serving past the allowance and charge for it, then write the rate - Kerne meters and bills the excess, no polling or manual invoicing. See [Designing your pricing](/guides/billing/designing-pricing#option-b-keep-going-and-charge-for-it-pay-as-you-go-past-the-included-amount) for the setup.

One thing to know before you rely on it: a *money* ceiling on a soft limit stops the charging, never the service. If you actually want consumption to stop, that's a separate ceiling in units, one rung below - see [why the cap doesn't block](/concepts/monetization/usage-billing#why-the-cap-doesnt-block).

## Where to enforce

### Backend middleware, for hard limits

The safest place to enforce a limit is your API layer - use `enforce()` if a thrown error fits your middleware pattern, or `allows()` if you'd rather branch yourself:

```typescript
if (!(await kerne.allows('api_calls', { subject: userId }))) {
  throw new ForbiddenError('You have reached your monthly API quota.');
}
```

If the action *is* the usage being counted, use [`consume()`](/sdks/server/entitlements/consume) instead - it checks and increments atomically, so a burst of concurrent requests can't all sneak past the limit at once.

### The client UI, for soft limits and upfront warnings

Don't wait for a "Save" click to tell users they've hit a limit - disable the button or show the upgrade nudge ahead of time, with [`useAccess`](/sdks/client/react/billing/check-entitlement) (it already handles the loading state):

```tsx
import { useAccess } from '@kerne/react';

function AddTeamMember() {
  const { allowed, isLoading } = useAccess('team_seats');

  return (
    <button disabled={isLoading || !allowed}>
      Add member {!isLoading && !allowed && ' (Upgrade required)'}
    </button>
  );
}
```

## Don't lose the user's work over it

Someone who spends 30 minutes writing a report and gets blocked on "Save" doesn't file a support ticket about your quota - they leave. "Error: storage limit reached" throws that work away. "Draft saved locally - upgrade to publish this report" doesn't. Check the limit before the resource-intensive step starts, not only when the user tries to submit its result.
